# Технології системного програмування — демонстрації

Демонстраційні програми до заняття 5 курсу «Системне програмування»
(ВСП «Фаховий коледж інформаційних систем і технологій КНЕУ ім. Вадима Гетьмана»).

Тема заняття — **бібліотека періоду виконання та засоби спостереження за програмою**: що саме додає до програми CRT і чого коштує відмова від неї; як програма сама повідомляє про свій стан і як цей стан побачити ззовні.

## Склад рішення

Рішення `Demo_Lecture_5.slnx`, чотири проєкти.

| Проєкт | Файл | Що показує |
|---|---|---|
| `Demo1_hello` | `hello.c` | той самий вихідний код, зібраний з `/MT` і `/MD`: різниця в розмірі файлу та в таблиці імпорту при незмінному коді |
| `Demo2_nocrt` | `nocrt.c` | та сама задача без CRT: власна точка входу `start`, вивід через `WriteConsoleW`, розбір командного рядка вручну, завершення через `ExitProcess` |
| `Demo3_worker` | `worker.c` | об'єкт спостереження: програма з видимим навантаженням, яка сама реєструє кожен крок у трьох каналах — ETW, `OutputDebugString` і консоль |
| `Demo4_dbgmon` | `dbgmon.c` | приймач `OutputDebugString` на 60 рядків: системний канал відлагодження — це спільна пам'ять і дві події ядра |

Проєкти 3 і 4 працюють у парі: перший пише, другий слухає.

## Як відкрити у Visual Studio

**Що має бути встановлено.** Visual Studio (Community достатньо) з компонентом **«Розробка класичних застосунків на C++»** (Desktop development with C++). Якщо його немає — запустіть Visual Studio Installer, натисніть *Modify* і позначте цей компонент.

**Крок 1. Відкрити рішення.** Двічі клацнути `Demo_Lecture_5.slnx` або у Visual Studio: *File → Open → Project/Solution* і вибрати цей файл. У Solution Explorer з'являться чотири проєкти.

> Файл рішення збережено в новому форматі `.slnx`. Його відкривають свіжі версії Visual Studio; якщо ваша версія повідомляє, що формат невідомий, оновіть Visual Studio або відкрийте потрібний проєкт напряму — *File → Open → Project/Solution* і вибрати `.vcxproj` у теці демонстрації.

**Крок 2. Перевірити конфігурацію.** На панелі зверху мають стояти **Debug** і **x64**. Розрядність тут не дрібниця: демонстрація 3 показує кількість дескрипторів процесу, а демонстрація 4 працює зі спільною пам'яттю — 32-розрядна збірка дасть інші числа й не побачить частини процесів.

**Крок 3. Вибрати проєкт для запуску.** У рішенні чотири окремі програми, тому Visual Studio треба сказати, яку саме запускати: у Solution Explorer клацнути правою кнопкою на потрібному проєкті → **Set as Startup Project**. Назва активного проєкту виділяється жирним.

**Крок 4. Зібрати.** *Build → Build Solution* (Ctrl+Shift+B).

> **Demo2_nocrt з рішення не збереться** — і це очікувано. У програми немає `main`, точка входу називається `start`, а стандартні бібліотеки підключати не можна. Компонувальник повідомить про нерозв'язане посилання на `main`. Цю демонстрацію збирають із командного рядка — див. розділ нижче; сама відмова збиратися звичайним способом і є частиною того, що вона показує.

**Крок 5. Запустити — обов'язково Ctrl+F5.** Комбінація **Ctrl+F5** (*Start Without Debugging*) залишає вікно консолі відкритим після завершення програми. Якщо натиснути F5, програма відпрацює й вікно миттєво закриється — ви нічого не встигнете прочитати.

Для демонстрації 3 є ще одна причина запускати саме через Ctrl+F5: під налагоджувачем Visual Studio перехоплює `OutputDebugString` і виводить рядки у своє вікно *Output*. Тоді до демонстрації 4 вони не дійдуть, і пара «пише — слухає» не спрацює.

**Крок 6. Передати аргументи командного рядка.** Демонстрація 3 приймає тривалість роботи в секундах. У Visual Studio аргументи задають так: правою кнопкою на проєкті → *Properties* → **Configuration Properties → Debugging → Command Arguments** → ввести значення (наприклад, `10`) → *OK*. Переконайтеся, що зверху у вікні властивостей вибрано ту саму конфігурацію — **Debug** і **x64**.

## Як зібрати з командного рядка

**Командний рядок** — Developer Command Prompt for VS (або Developer PowerShell).

**Демонстрація 1 — двічі з того самого файлу:**

```
cl /utf-8 /MT hello.c /Fe:hello_mt.exe
cl /utf-8 /MD hello.c /Fe:hello_md.exe
```

**Демонстрація 2 — компіляція й компонування окремо:**

```
cl /utf-8 /O1 /GS- /c nocrt.c
link /nologo /nodefaultlib /entry:start /subsystem:console nocrt.obj kernel32.lib
```

`/nodefaultlib` відрізає стандартні бібліотеки, `/entry:start` призначає точку входу замість `mainCRTStartup`, `/GS-` вимикає перевірку переповнення стека — вона теж реалізована в CRT. Прибрати будь-який із цих ключів — і компонування не пройде.

**Демонстрації 3 і 4:**

```
cl /utf-8 /W4 worker.c
cl /utf-8 /W4 dbgmon.c
```

Прапорець `/utf-8` обов'язковий у всіх випадках: вихідні файли збережено в UTF-8, і без нього кириличні рядки буде зіпсовано вже на етапі компіляції.

## Як запускати

**Демонстрація 1 — порівняти, а не запустити.** Обидві програми виводять однакове. Дивитися треба на файли:

```
dir hello_mt.exe hello_md.exe
dumpbin /imports hello_md.exe
dumpbin /imports hello_mt.exe
```

При `/MD` в імпорті будуть `VCRUNTIME140.dll` і набори `api-ms-win-crt-*`, при `/MT` — практично сам `KERNEL32.dll`, зате файл більший приблизно вдесятеро.

**Демонстрація 2:**

```
nocrt.exe
nocrt.exe будь-які аргументи
```

Програма надрукує сирий командний рядок повністю — розібраного `argv` без CRT не існує.

**Демонстрації 3 і 4 — у двох вікнах.** Спочатку в першому вікні запустити приймач:

```
dbgmon.exe
```

Потім у другому — програму, за якою спостерігаємо:

```
worker.exe          працює 20 секунд (типово)
worker.exe 10       працює 10 секунд
```

У вікні приймача з'являться ті самі рядки, що й у консолі `worker.exe`, з номером процесу-відправника.

Якщо `dbgmon.exe` повідомляє, що не вдалося створити об'єкти ядра, — у системі вже запущено інший приймач (найчастіше DebugView). Канал `OutputDebugString` один на всю сесію, і другий слухач до нього не підключиться.

`worker.exe` навмисно лишає частину дескрипторів і пам'яті незвільненими, доки працює: у виводі видно, як зростає їх кількість. Перед виходом програма прибирає все за собою — про це повідомляє рядок `WARN`. Поки вона працює, її стан видно і ззовні:

```
tasklist /fi "IMAGENAME eq worker.exe"
```

## Що ще є в теці

**Трасування ETW.** `worker.c` реєструє постачальника `Demo03.Worker` і пише події через TraceLogging. Щоб їх зібрати, потрібні окремі засоби (`wpr`, `tracelog`, Windows Performance Analyzer) — на занятті це показують готовим файлом трасування.

**Журнал у файл.** У поточній редакції `worker.c` запис у `demo03.log` **закоментовано** — працюють лише канали ETW, `OutputDebugString` і консоль. Щоб увімкнути третій канал, розкоментуйте рядок із `fputs(line, g_log)` у функції `log_line`.

**Тека `Demo_Lecture_5/`.** Містить порожній проєкт, що лишився від створення рішення; у `.slnx` він не згадується і на збирання не впливає.
